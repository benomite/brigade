A cook that finds the ticket already done closes it as served

Story of November 2026 · ticket #3146 · pull request #3148

The ticket

Issue #3146 starts from something seen on a served project on 2026-11-09. A ticket's fix had already landed on main through another pull request. Three cooks in a row took the ticket, found the fix there and stopped, saying "no code change is needed, the fix is already on main". The station counted each of them as a cook without a delivery, and after three it set the ticket aside as served-elsewhere. The ticket then sat on the rail with no cook and no question.

The issue puts it in one line: "A cook that proves the work is already done has served the ticket. That is not a failure." Its acceptance criteria ask that such a ticket be closed as served, with a comment naming the commit or pull request that satisfied it, but only once the claim is checked: the commit is on the integration branch and the gates are green.

From issue to merge

All times are UTC, on 2026-11-10, as GitHub records them on the issue, the pull request and its checks.

  1. 10:02 — Issue opened. #3146, "A cook that finds the ticket already done on main closes it as served, not as a failure".
  2. 10:04 — The manager puts it on the rail: fire, calibrated sonnet / medium, because "It is a bounded change to existing station logic (…), not a new product surface".
  3. 10:05 — Taken by station box/claude: a cook starts on the ticket.
  4. 10:09 — The cook delivers. Pull request #3148 opens with commit e43b950: the station recognizes a cook that ends with <deja-servi>, checks its claim and closes the ticket as served.
  5. 10:09 — The pass: the review approves. The reviewer read the whole diff, found that it "does what the ticket asks", and left four remarks, none blocking.
  6. 10:12 — The pass: one CI check is red. windows tests (1/8) fails; every other check of e43b950 is green, the gates included.
  7. 10:12 — Sent back to a cook (1/2): "the CI is red on e43b950: windows tests (1/8) (failed step: Tests du runtime)".
  8. 10:13 — Taken again by station box/claude.
  9. 10:13 — The cook fixes it with commit be1ab01: one line of runtime/test/deja-servi.test.ts.
  10. 10:18 — Merged. Pull request #3148 lands on main, every check of be1ab01 green, and the issue closes two seconds later.

What the pass sent back, and why

The review had nothing blocking to say. The send-back came from the CI. On Windows, the runtime test garde-duree.test.ts, which walks the whole test folder, failed with:

test/deja-servi.test.ts:114 : garde delaiMs: 30_000 = 30000 ms, la limite est 2000 ms

The new test gave its fake gates a 30 s guard. The repository's rule is that no guard in a test exceeds 2 s. The gates of the pull request had not played garde-duree.test.ts, because a test that walks a folder instead of importing what it checks is never close to a diff; only the Windows CI, which plays every file, saw it.

The second cook changed that one line, gates: { delaiMs: 30_000 } to gates: { delaiMs: 1_500 }, with the commit message "la garde des gates du test déjà-servi tient sous la limite de 2 s". Nothing else moved, and the pull request merged on that commit.

After the merge

The same morning, #3146 was one of the tickets counted in the quality ticket #3150, opened by a station because the first-try rate had fallen to 65%, under its 70% threshold. Its fix, commit a000db7 merged with #3152, says: "the cook plays the tests that guard a whole folder, which no diff makes close — the cause of #3089, #3090 and #3146's red runtime tests".
