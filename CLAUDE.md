## Équipe multi-agents (plugin brigade)

- **Acteurs** : le chef, le second (en local) et la cuisine (runtime, manager, cooks, pass)
- **Interface** : tout travail d'interface est porté par le cook design de la cuisine (#837)
- **Branche d'intégration** : `v2`
- **Worktrees** : `<parent du dépôt>/brigade-wt/<n>-<slug>` — frère du dépôt, le parent se calcule (`dirname "$(git rev-parse --show-toplevel)"`)
- **Setup worktree** : `.claude/brigade/worktree-setup.sh <n> <WT>`
- **Gates** : `.claude/brigade/gates.sh <WT>`, puis `/code-review`
- **Zones de fichiers** : trois zones de produit, qui n'ont pas les mêmes règles.
  - **Runtime** — `runtime/` : le runtime de la V2, TypeScript exécuté par Node 26, avec son `package.json`. Une issue runtime écrit ici, et nulle part dans la zone plugin.
  - **App** — `app/` : l'app desktop de la V2 (Electron, xterm.js, node-pty), TypeScript sans build, avec son `package.json`. Une issue app écrit ici, et n'ajoute **rien** au runtime : l'app lance les commandes qui existent, elle n'en double aucune. `app/src/vue/` (la peau) est portée par le cook design (#837). La maquette est dans `docs/maquettes/app/` ; un ticket d'app cite l'écran qu'il sert.
  - **Plugin V1** — `commands/` (définition des rôles), `agents/` (le dev-teammate spawné), `codex/skills/` (miroir Codex, source que `/brigade:sync` copie chez le projet consommateur), `.claude-plugin/` (manifests). `evals/` porte les cas d'évaluation de ces rôles.
  - **Communs** — `scripts/` (outillage de release), `docs/`, `.claude/brigade/` (gates et setup de worktree).
- **Dev local** :
  - **Runtime** — Node 26, sans build. Tests : `npm --prefix runtime test` (ils passent sur un clone nu, sans rien installer). Contrôle de types : `npm --prefix runtime run typecheck` (réclame les dépendances de dev, posées par le setup de worktree). Lancer : `npm --prefix runtime start`, après le setup — l'état vit dans `$BRIGADE_STATE_DIR`. **Neuf variables sont obligatoires** (`BRIGADE_STATE_DIR`, `BRIGADE_PROJECT`, `BRIGADE_GITHUB_REPO`, `BRIGADE_REPO_DIR`, `BRIGADE_BASE_BRANCH`, et le calibrage du manager et du reviewer : `BRIGADE_MANAGER_MODEL`, `BRIGADE_MANAGER_EFFORT`, `BRIGADE_REVIEWER_MODEL`, `BRIGADE_REVIEWER_EFFORT`) : le setup n'en pose qu'une, les huit autres sont à toi, et le runtime refuse de démarrer en nommant celle qui manque. Le détail est dans `docs/runtime/exploitation.md` (« Cinq variables, aucun défaut » et « Sur le poste de dev »). **La doc du runtime est découpée en pages : ouvre d’abord l’index `docs/runtime/README.md`, puis seulement les pages de ta partie** (`docs/runtime.md` n’est qu’un renvoi vers cet index). **Lancé ainsi, c'est une vraie cuisine : `start` lance de vrais cooks sur le quota Max, sans demande de permission.** Les commandes du chef se lancent par `npm --prefix runtime run <commande>` : `journal` (relire le journal), `rail` (le rail des tickets), `garde-fous` (voir et régler les plafonds), `base` (voir la base d'intégration, faire rejouer ses gates quand elle est rouge), `installation` (vérifier qu'un projet est prêt à être servi — le parcours est dans `docs/installer.md`), plus `status`, `station`, `pass` et `grant` — la liste fait foi dans `runtime/package.json`. Aucun démon ne tourne sur le poste de dev ; les tests pilotent un faux `claude` (`BRIGADE_CLAUDE_BIN`) et ne consomment aucun quota.
  - **App** — Tests : `npm --prefix app test` ; contrôle de types : `npm --prefix app run typecheck` — les deux réclament les dépendances, posées par le setup de worktree **sans le binaire d'Electron** (311 Mo), qu'aucun test ne lance. Lancer : `npm --prefix app start`, qui pose ce binaire au premier lancement. **Lancée ainsi, c'est une vraie app : chaque espace ouvert lance un vrai `claude` dans le dossier du projet** — pour l'essayer sans quota, `BRIGADE_CLAUDE_BIN=app/test/aides/faux-claude.sh` et `BRIGADE_APP_CONFIG=<un fichier d'essai>`. **Et un projet qui déclare `hote` (le nom par lequel ton `ssh` joint sa box) est lu par un vrai `ssh` toutes les trente secondes** — `BRIGADE_SSH_BIN=<un faux ssh>` pour l'essayer sans box. Les projets se déclarent dans `~/.config/brigade/app.json`, hors du dépôt. Le détail est dans `docs/app.md`.
  - **Plugin V1** — rien à lancer. Pour éprouver un rôle modifié, il faut l'installer : bumper `version` dans `.claude-plugin/plugin.json`, puis `scripts/update-partout.sh`. Le plugin publié vient de `main`, pas de `v2` : le chemin de release (même version des deux côtés, bump sur `main` d'abord, report chemin par chemin) est écrit dans `scripts/README.md`.
  - **Ce que le setup attribue à un worktree** — `BRIGADE_STATE_DIR=<WT>/.brigade-state` (base locale `log.db`, verrou `lock.db`, `runs/` ; ignoré par git) et `BRIGADE_PORT=20000 + <n° d'issue>`. Deux worktrees ont deux répertoires et deux ports : ils ne se croisent pas. N'écris jamais un chemin d'état ni un port en dur. Les tests n'utilisent ni l'un ni l'autre : chacun crée son répertoire temporaire et écoute sur le port 0.
- **Doc vivante** : `docs/` — toute livraison qui change le comportement d'un rôle met à jour la doc concernée sous `docs/`.
- **Specs / plans** : `docs/superpowers/specs/<AAAA-MM-JJ>-<slug>.md`
- **Doc produit** : `README.md` — c'est lui qui décrit le protocole tel que l'utilisateur le vit (rôles, handoffs, règles non négociables).

### Conventions propres à ce dépôt

- **Dans la zone plugin, le miroir Codex n'est pas optionnel.** Toute modification d'un `commands/<rôle>.md` doit être répercutée dans `codex/skills/<rôle>/`. Les gates l'exigent : un rôle modifié depuis la branche d'intégration sans que rien ne bouge sous son miroir les rend rouges. Elles voient que le miroir a bougé, pas qu'il dit la même chose — la justesse reste au dev. Un changement qui ne touche que `runtime/` ou `app/` ne doit rien au miroir.
- **Les gates jouent les tests du runtime, puis ceux de l'app**, dès que le `package.json` de la zone existe, et son contrôle de types s'il est déclaré. Une zone absente n'est pas un échec. Ni réseau, ni vrai `claude`, ni écran : **aucun test ne lance Electron** — ce qui se prouve de l'app vit dans des modules joués par `node --test`, la vue reste mince. Les tests de l'app sur un vrai pty sont sautés, en le disant, là où node-pty n'est pas livré compilé (Linux).
- **Plusieurs suites tournent en même temps sur la machine** — les gates de chaque dev — et chacune prend alors trois à quatre fois son temps. Un test ne doit donc **jamais courir contre l'horloge** : il attend un fait (`jusqua`, un fichier posé, un process mort), pas une durée. Un délai n'y est qu'une garde, large, pour qu'un test cassé finisse par le dire ; un vrai minuteur du runtime réglé court dans un test (inactivité, plafond des gates) doit rester vrai quand tout met dix fois plus de temps à démarrer. Rien n'est partagé entre deux worktrees que le cache de compilation de Node, qui n'est qu'un cache. Pour l'éprouver : plusieurs `npm --prefix runtime test` de front, plusieurs fois.
- **Ne tue jamais un process par son nom** (`pkill -f src/main.ts`) : les tests de tous les worktrees lancent de vrais `main.ts`, et tu ferais échouer la suite d'un autre. Un test bloqué se tue par son pid. Celui qui *attend* sans fin s'arrête seul : au bout de deux minutes il est en échec, nommé, et le process de son fichier sort aussitôt, même s'il tient encore un minuteur ou un process enfant (`--test-force-exit`) — les gates rendent donc la main, rouges. Un test bloqué dans du code **synchrone** (une boucle) n'est arrêté par aucun minuteur de son lanceur : c'est la **garde d'horloge** des gates qui le rattrape — passé `300 s` (`BRIGADE_GATES_DELAI_TESTS`, en secondes entières), `gates.sh` tue le groupe de process de la suite, fichiers de tests compris, et rougit (`FAIL  tests du runtime arrêtés par la garde d'horloge`). Elle ne nomme pas le test, et elle ne garde que les gates : un `npm --prefix runtime test` lancé à la main reste retenu. Une chose n'est pas tenue : un process qu'un test a lancé sans le tuer en fin de test lui survit.
- **Un test du runtime ou de l'app en échec dans les gates se lit sans rejouer** : son nom et son erreur sont dans la sortie des gates, et la sortie entière de la suite est gardée dans `.brigade-state/gates/` du worktree (une semaine). Un rouge qui ne se reproduit pas se diagnostique là — pas en rejouant jusqu'à ce qu'il revienne.
- **Un rôle ajouté doit être déclaré** dans `commands` de `.claude-plugin/plugin.json`, sinon il ne se charge jamais. Les gates attrapent l'oubli.
- **Une mise à jour du plugin ne change pas la session en cours** : les rôles sont chargés au démarrage. Ne jamais attendre d'une orchestration en cours qu'elle prenne un correctif fraîchement publié.
