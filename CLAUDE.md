## Équipe multi-agents (plugin brigade)

- **Rôles actifs** : PO, Manager, Dev, Designer
- **Roadmap** : issue #1 (writer unique = Manager)
- **Branche d'intégration** : `v2`
- **Worktrees** : `<parent du dépôt>/brigade-wt/<n>-<slug>` — frère du dépôt, le parent se calcule (`dirname "$(git rev-parse --show-toplevel)"`)
- **Setup worktree** : `.claude/brigade/worktree-setup.sh <n> <WT>`
- **Gates** : `.claude/brigade/gates.sh <WT>`, puis `/code-review`
- **Plafond des gates** : `131 s` de processeur — ce que coûte un passage complet, utilisateur et système, compté par les gates elles-mêmes ; franchi, elles rougissent et disent de combien. Il juge juste poste calme (voir les conventions plus bas)
- **Zones de fichiers** : deux zones de produit, qui n'ont pas les mêmes règles.
  - **Runtime** — `runtime/` : le runtime de la V2, TypeScript exécuté par Node 26, avec son `package.json`. Une issue runtime écrit ici, et nulle part dans la zone plugin.
  - **Plugin V1** — `commands/` (définition des rôles), `agents/` (le dev-teammate spawné), `codex/skills/` (miroir Codex, source que `/brigade:sync` copie chez le projet consommateur), `.claude-plugin/` (manifests). `evals/` porte les cas d'évaluation de ces rôles.
  - **Communs** — `scripts/` (outillage de release), `docs/`, `.claude/brigade/` (gates et setup de worktree).
  - Le Designer n'a **pas de peau** ici : ce dépôt n'a aucune UI — son terrain est le rendu textuel des rôles (formulations, tableaux, lisibilité en terminal), pas un thème.
- **Dev local** :
  - **Runtime** — Node 26, sans build. Tests : `npm --prefix runtime test` (ils passent sur un clone nu, sans rien installer). Contrôle de types : `npm --prefix runtime run typecheck` (réclame les dépendances de dev, posées par le setup de worktree). Lancer : `npm --prefix runtime start`, après le setup — l'état vit dans `$BRIGADE_STATE_DIR`. **Neuf variables sont obligatoires** (`BRIGADE_STATE_DIR`, `BRIGADE_PROJECT`, `BRIGADE_GITHUB_REPO`, `BRIGADE_REPO_DIR`, `BRIGADE_BASE_BRANCH`, et le calibrage du manager et du reviewer : `BRIGADE_MANAGER_MODEL`, `BRIGADE_MANAGER_EFFORT`, `BRIGADE_REVIEWER_MODEL`, `BRIGADE_REVIEWER_EFFORT`) : le setup n'en pose qu'une, les huit autres sont à toi, et le runtime refuse de démarrer en nommant celle qui manque. Le détail est dans `docs/runtime.md` (« Neuf variables, aucun défaut » et « Sur le poste de dev »). **Lancé ainsi, c'est une vraie cuisine : `start` lance de vrais cooks sur le quota Max, sans demande de permission.** Les commandes du chef se lancent par `npm --prefix runtime run <commande>` : `journal` (relire le journal), `rail` (le rail des tickets), `garde-fous` (voir et régler les plafonds), `base` (voir la base d'intégration, faire rejouer ses gates quand elle est rouge), `installation` (vérifier qu'un projet est prêt à être servi — le parcours est dans `docs/installer.md`), plus `status`, `station`, `pass` et `grant` — la liste fait foi dans `runtime/package.json`. Aucun démon ne tourne sur le poste de dev ; les tests pilotent un faux `claude` (`BRIGADE_CLAUDE_BIN`) et ne consomment aucun quota.
  - **Plugin V1** — rien à lancer. Pour éprouver un rôle modifié, il faut l'installer : bumper `version` dans `.claude-plugin/plugin.json`, puis `scripts/update-partout.sh`.
  - **Ce que le setup attribue à un worktree** — `BRIGADE_STATE_DIR=<WT>/.brigade-state` (base locale `log.db`, verrou `lock.db`, `runs/` ; ignoré par git) et `BRIGADE_PORT=20000 + <n° d'issue>`. Deux worktrees ont deux répertoires et deux ports : ils ne se croisent pas. N'écris jamais un chemin d'état ni un port en dur. Les tests n'utilisent ni l'un ni l'autre : chacun crée son répertoire temporaire et écoute sur le port 0.
- **Doc vivante** : `docs/` — toute livraison qui change le comportement d'un rôle met à jour la doc concernée sous `docs/`.
- **Specs / plans** : `docs/superpowers/specs/<AAAA-MM-JJ>-<slug>.md`
- **Doc produit** : `README.md` — c'est lui qui décrit le protocole tel que l'utilisateur le vit (rôles, handoffs, règles non négociables).
- **Skills en boucle** : PO → `superpowers:brainstorming` puis `superpowers:writing-plans` quand une idée part en spec ; Dev → selon la zone : `superpowers:test-driven-development` sur le runtime, `superpowers:writing-skills` sur le plugin V1 (le produit livré y *est* du markdown de skill, ses règles s'appliquent) ; Manager → aucune ; Designer → aucune.

### Conventions propres à ce dépôt

- **Dans la zone plugin, le miroir Codex n'est pas optionnel.** Toute modification d'un `commands/<rôle>.md` doit être répercutée dans `codex/skills/<rôle>/`. Les gates l'exigent : un rôle modifié depuis la branche d'intégration sans que rien ne bouge sous son miroir les rend rouges. Elles voient que le miroir a bougé, pas qu'il dit la même chose — la justesse reste au dev. Un changement qui ne touche que `runtime/` ne doit rien au miroir.
- **Les gates jouent les tests du runtime** dès que `runtime/package.json` existe, puis le contrôle de types s'il est déclaré. Un runtime absent n'est pas un échec. Ni réseau, ni vrai `claude`.
- **La durée des gates a un plafond, et il se compte en temps processeur** : `131 s`, déclaré par le binding **Plafond des gates**. Les gates additionnent ce qu'elles ont consommé (elles-mêmes et tout ce qu'elles ont lancé, temps utilisateur et temps système), l'impriment à chaque passage, et rougissent au-delà — `FAIL  plafond des gates franchi`, avec le dépassement en secondes et en pourcentage. La ligne `durée des gates :` porte de quoi lire un passage sans le rejouer : `84,9 s de processeur (46,6 utilisateur + 38,3 système), 16 s d'horloge, charge du poste 5,70 (plafond : 131 s)` — la charge est la moyenne sur une minute à l'arrivée. **Le plafond juge juste poste calme, et seulement là.** Mesuré le 2026-10-09 sur dix cœurs, même tête (`43467a4`, 1078 tests qui lancent de vrais sous-process : faux `claude` en shell, faux `gh`, git, bash, quelques centaines de CLI dans un vrai Node), douze passages de `gates.sh` un à la fois : à charge 6, **84 à 85 s de processeur** (46 utilisateur + 38 système) pour 16 s d'horloge ; à charge 6 à 21 au départ, 95 à 103 s (51 à 56 + 43 à 47) pour 20 à 26 s ; poste saturé (charge 16 à 27 au départ, jusqu'à 114 en cours), 121 à 141 s (65 à 75 + 56 à 66) pour 24 à 132 s. Du calme au pire : utilisateur ×1,6, système ×1,7, horloge ×8. **Aucune grandeur ne s'en affranchit** : l'horloge est la pire ; le temps utilisateur seul gonfle du même pas que le système (leur rapport reste à 0,8–0,9 partout), le compter seul ne changerait que le chiffre ; le compte d'instructions (`/usr/bin/time -l`) ne couvre pas les process descendants ; et la charge sur une minute prédit mal le surcoût (95 s à « 5,8 », 99 s à « 21 », 128 s à « 23 »), donc elle s'imprime et n'excuse rien. Le plafond est fixé sur `v2` (`d426f44`, 1228 tests, après le jalon 7), mesuré le 2026-10-09 par `gates.sh` de la branche, un passage à la fois : 105,0 s (charge 4,9 → 7,8), 100,6 s (4,2 → 8,5), 107,0 s (8,5 → 12,7), 120,8 s (12,4 → 16,4, rouge sous l'ancien plafond de 120 s, sans qu'aucun test n'ait été ajouté). Le plus cher des passages à charge ≤ 8 est 105,0 s ; plus un quart : 131 s. Il avait été fixé à 120 s sur 1129 tests (95,2 s au calme) ; la suite a grossi, la marge de 14 % ne tenait plus. **Au-delà, il peut rougir seul**, sans qu'aucun test n'ait été ajouté : ce rouge-là se reconnaît à la charge et à l'horloge de sa ligne, et se rejoue au calme avant de toucher à la suite ou au chiffre. Le plafond ne voit pas non plus un test qui *attend* (un `sleep`, un délai réel) : celui-là reste l'affaire de la convention suivante. Un plafond franchi au calme se traite en allégeant la suite ou en le relevant **dans la même PR, chiffre mesuré à l'appui** ; le relever est une décision qui se lit dans le diff, pas une dérive. Retirer la ligne du binding retire le plafond.
- **Plusieurs suites tournent en même temps sur la machine** — le hook d'arrêt de chaque session, les gates de chaque dev — et chacune prend alors trois à quatre fois son temps. Un test ne doit donc **jamais courir contre l'horloge** : il attend un fait (`jusqua`, un fichier posé, un process mort), pas une durée. Un délai n'y est qu'une garde, large, pour qu'un test cassé finisse par le dire ; un vrai minuteur du runtime réglé court dans un test (inactivité, plafond des gates) doit rester vrai quand tout met dix fois plus de temps à démarrer. Rien n'est partagé entre deux worktrees que le cache de compilation de Node, qui n'est qu'un cache. Pour l'éprouver : plusieurs `npm --prefix runtime test` de front, plusieurs fois.
- **Ne tue jamais un process par son nom** (`pkill -f src/main.ts`) : les tests de tous les worktrees lancent de vrais `main.ts`, et tu ferais échouer la suite d'un autre. Un test bloqué se tue par son pid. Celui qui *attend* sans fin s'arrête seul : au bout de deux minutes il est en échec, nommé, et le process de son fichier sort aussitôt, même s'il tient encore un minuteur ou un process enfant (`--test-force-exit`) — les gates rendent donc la main, rouges. Un test bloqué dans du code **synchrone** (une boucle) n'est arrêté par aucun minuteur de son lanceur : c'est la **garde d'horloge** des gates qui le rattrape — passé `300 s` (`BRIGADE_GATES_DELAI_TESTS`, en secondes entières), `gates.sh` tue le groupe de process de la suite, fichiers de tests compris, et rougit (`FAIL  tests du runtime arrêtés par la garde d'horloge`). Elle ne nomme pas le test, et elle ne garde que les gates : un `npm --prefix runtime test` lancé à la main reste retenu. Une chose n'est pas tenue : un process qu'un test a lancé sans le tuer en fin de test lui survit.
- **Un test du runtime en échec dans les gates se lit sans rejouer** : son nom et son erreur sont dans la sortie des gates et dans le réveil du hook, et la sortie entière de la suite est gardée dans `.brigade-state/gates/` du worktree (une semaine). Un rouge qui ne se reproduit pas se diagnostique là — pas en rejouant jusqu'à ce qu'il revienne.
- **Un rôle ajouté doit être déclaré** dans `commands` de `.claude-plugin/plugin.json`, sinon il ne se charge jamais. Les gates attrapent l'oubli.
- **Une mise à jour du plugin ne change pas la session en cours** : les rôles sont chargés au démarrage. Ne jamais attendre d'une orchestration en cours qu'elle prenne un correctif fraîchement publié.
- **Les gates se rejouent seules à l'arrêt**, par un hook `Stop` **et** `SubagentStop` en `asyncRewake` (`.claude/brigade/gates-hook.sh`) — les deux événements, parce que `Stop` ne se déclenche pas quand un subagent termine, et que les dev-teammates en sont. Ce hook **ne remplace pas** le passage de gates de ta Definition of Done : il rattrape ce qui aurait été oublié. Vertes, elles se taisent ; rouges, elles te réveillent — **deux fois sur un même échec, quatre fois en tout**, puis elles te demandent de signaler `bloqué` et se taisent. Un arrêt qui n'a rien changé depuis le précédent ne consomme pas de réveil. Limite connue : le hook ne sait pas à qui attribuer un arbre rouge, donc une session qui n'y est pour rien peut être réveillée une fois. Sans ces plafonds, le hook boucle à l'infini — mesuré le 2026-10-05, et de nouveau quand l'empreinte de l'échec change à chaque tour.
